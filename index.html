Grounding LSC Delivery to Your Team

Bottom line: The agent isn't the hero of this story — your architects are. How to bring the LSC Delivery Architect to your own competency: prototype-first Solution Plans, Salesforce-grounded mockups, and implementation-ready user stories.

Start Here

Every LSC engagement argues about the same two questions — too late.

01

Stories Arrive Before Shape

Product owners are asked to sign off on Given/When/Then acceptance criteria before they have seen a single screen. So they hedge, and refinement runs another two sprints.

02

"Can We Do This Out of the Box?"

The build-technology call — Dynamic Actions, Screen Flow, LWC, OmniScript — gets made after the estimate is already committed. That is where the cost surprise lives.

03

Mockups That Mislead

A polished wireframe shows a feature that looks free and builds expensive. Nothing on it says which control is standard Salesforce and which is a custom component.

An ungrounded prototype is just a picture. It shows the product owner exactly what they hoped to see, and hides everything it will cost to build.

The Shift

LSC delivery doesn't need more acceptance criteria. It needs the build made visible first.

Before anyone writes a Given/When/Then line, the product owner should be able to click the feature and see, on every control, whether it is standard Salesforce or something we have to build.

Today

Stories first, mockup maybe, build technology decided last. Personas drift to "as a user", records are specified as "and related fields are updated", and the developer books a follow-up meeting before writing a line of code.

LSC Delivery Architect

Plan and prototype first, grounded in a declarative-first build decision. Stories follow once the product owner has walked the mockup and agreed to the shape — with every field enumerated.

From the skill contract

"A prototype without the grounding is worse than no prototype — it misleads the PO on cost shape. That's the whole point."

✨

The agent already knows the LSC personas, the ~350 standard objects, the Veeva translation, and the Concur expense model — so no architect starts from a blank page, and no one carries the standard alone. We stop re-deriving what "good" looks like and spend the time on the judgment calls only our architects can make.

STEP 0 · Smart Routing

Six modes, detected from how you phrase the ask

ModeTriggered byBehaviour
Plan + Prototype"plan and prototype", "no stories yet"Phase 1–2 questions only, then plan + mockup. Story blockers deliberately skipped.
New Feature"write a user story for…"Full Phase 1–4 question flow, then a complete story.
Epic Breakdown"break down this spec"Decomposition plan for approval, then up to ten cross-referenced stories.
Veeva → LSC"migrate", "from Veeva"Translate every term to LSC-native; keep the Veeva original in a source header only.
Refactor"change existing", "modify"Skip sub-domain selection; start at technical discovery.
Bug Fix"defect", "broken", "fix"Skip vertical questions; focus on current versus expected behaviour.
The hard blockers — an artifact does not ship without these
1

Concrete LSC persona

Field Sales Representative, MSL, KAM, Event Organizer. Never "user". HCPs are the subject of the work, not the login role.

2

Business-language GWT

Three explicit lines, one When. No Apex class names, OmniScript step numbers, SOQL, or API field names inside an AC.

3

Per-field record spec

Every "records are created or updated" outcome enumerates each object and each field with its exact value. Never "etc."

4

Declarative-first decision

Dynamic Actions, Screen Flow, and Field Sets are considered before OmniScript. OmniStudio is one option, not the default.

No invented names. Custom components are verified through the code-review-graph index; standard LSC objects and fields through the salesforce-docs index. Anything that cannot be verified is written as (proposed) rather than asserted — because a confidently wrong object name is the one error that survives all the way to a sprint commitment.

Artifact 3 — Implementation-Ready Story

What a developer receives when the plan is promoted

requirements/LSC_HcoParentChildHierarchyView_UserStory.md
HCO Parent–Child Hierarchy View

Persona: Key Account Manager (KAM) · Sub-domain: Commercial · Priority: P1

The Story

As a Key Account Manager, I want to see the full parent–child structure of a health care organization on the account record, so that I can plan coverage against the whole system instead of one site at a time.

Acceptance Criteria — Pattern A

Given I am viewing a health care organization that has affiliated child sites
When I open the Hierarchy tab on the account
Then each child site is listed beneath its parent with site name, city, and affiliation status
And sites whose affiliation has ended are excluded from the active count

Edge case is mandatory, not optional

Given a health care organization has no affiliated child sites
When I open the Hierarchy tab
Then an empty state explains that no affiliations exist and offers to record one

Business language is enforced

No Apex class name, OmniScript step number, SOQL query, or *__c API name appears inside any Given/When/Then line. All of it moves to Technical Implementation — which is why QA can execute the criteria without a developer translating first.

PersonaPattern APattern ETech ImplEffort

Technical Implementation (high-level)

A concise table after the criteria — component, change type, one-line note, and the AC numbers it implements. Declarative options are named first, with the reason the simpler one was or was not enough.

Estimated Effort

Component-level sizing from S to XXL, always labelled AI-estimated — validate with team, because a number that looks authoritative is worse than one that admits it needs a human check.

Structure and contract are real; this excerpt is condensed for the session. The full story lives in requirements/.

What the agent asks before it writes anything
The agent handles
  • Detecting the workflow mode from your phrasing
  • Loading the right sub-domain object model
  • Verifying component and object names, or marking them proposed
  • Scanning requirements/ for stories that overlap or conflict
  • Choosing the declarative-first build technology and saying why
You still decide
  • Commercial, Medical, or Market Access — and net-new versus Veeva migration
  • The persona and the business outcome
  • Regulatory scope: sample accountability, consent, Open Payments
  • Which markets, product families, and account types are in scope
  • Whether the estimate is credible — the sizing is a starting point

Build It Yourself

Install once, then work in plain language.

Five steps. Run the validation after each one — the value is real before you reach the end.

The skill lives under .cursor/, which Cursor auto-loads. Clone this repository and copy the payload into the project where you plan your LSC work.

Terminalgit clone https://github.com/dipankardixit-ai/afls-architects.git cd afls-architects ./install.sh /path/to/your-project

Prefer it available in every workspace? Copy skills/lsc-delivery-architect into ~/.cursor/skills/ and the .mdc rule into ~/.cursor/rules/. Confirm the exact user path under Cursor → Settings → Rules & Skills.

Then reload the Cursor window. A skill added while Cursor is running is not always picked up until the window reloads — this is the single most common reason it "didn't work".
Checkpoint

Confirm the skill is actually loaded before you rely on it.

PromptPlan and prototype a test capability — no stories yet.

What good looks like: it announces Plan + Prototype mode, confirms no stories will be written, and asks Phase 1 and Phase 2 questions only — as a structured multiple-choice picker, not a wall of prose.

This is the mode built for product-owner conversations. Name the capability and say explicitly that stories come later.

PromptPlan and prototype the HCO parent–child hierarchy view for Key Account Managers — no stories yet.

You get two files: a Solution Plan with the build-technology decision and component inventory, and a clickable prototype where every element is badged with the component that will implement it.

  • Answer the clarifying questions — vertical, persona, and regulatory scope change which objects are named
  • Open the prototype and click through it with the product owner in the room
  • Check the legend footer against the plan's effort sizing before anyone commits a number

Once the product owner has agreed to the shape, the plan becomes the input to Epic Breakdown — so the stories inherit the build decision instead of re-opening it.

PromptPromote that plan to full user stories.

Every story arrives with a concrete persona, business-language criteria, a per-field record spec on each write, a Technical Implementation table, Definition of Done, and effort sizing.

Paste the Veeva requirement verbatim. The agent translates the mechanics and keeps the business intent, recording the original in a source header rather than the story body.

PromptMigrate this Veeva story to Salesforce LSC: "As a Field Rep, I need a Sample Inventory screen to view my on-hand sample lots and initiate sample orders, so I can manage inventory and stay PDMA compliant."
  • Call becomes Visit · Sample Lot becomes Production Batch Item · Action Bar becomes Action Launcher
  • The persona is re-anchored to a real login role — the HCP is the subject, never the user
  • Anything with no clean LSC equivalent is raised as a clarification, not quietly guessed

Stress-test routing: give it a task from each mode without naming the mode, and see which contract it reaches for.

PromptValidate my LSC Delivery Architect setup. Confirm the skill and rule are loaded, list which references you can read, and tell me which workflow mode you would route each of these to: a Concur expense enhancement, a defect in medical inquiry intake, and a scope document with eight capabilities.
  • Concur enhancement: should reach for the Concur integration reference
  • Defect: should route to Bug Fix and skip the vertical questions
  • Scope document: should route to Epic Breakdown and propose a decomposition before generating

What good looks like: it names the mode it detected and why. If it cannot explain the routing, the rule file is not being applied — reload the window and check the file landed in .cursor/rules/.

Start with one step. Installing and running a single Plan + Prototype is enough to change the next product-owner conversation. You do not need all five before it earns its place.
Beyond setup: working practices

Do

Keep engagement specifics — stakeholders, org constraints, which release you are targeting — in the project, and let the skill stay generic. Point at the skill; do not restate it.

Avoid

Don't fork the skill for one client. If a gap shows up, fix the shared reference so every future engagement benefits. Keep client names out of skills/ entirely.

Keep it healthy

Per release — object catalog check

PromptReview the LSC standard-object catalog reference against the current API version. What objects or fields have been added, renamed, or deprecated since Summer '26 / v67.0?

Quarterly — run the evaluations

PromptRun each scenario in evaluations/ against this skill and score the output on every expected_behavior item. Report which blockers failed.

Evaluations are the source of truth for whether the skill still works — extend them before extending the documentation.

Scale to Your Team

The Pattern

Publish once, install everywhere

One owner maintains the merged skill; everyone else pulls it down. Same mechanism your team already uses for shared libraries.

git clone https://github.com/dipankardixit-ai/afls-architects.git
./install.sh /path/to/your-project

This repository is the AFLS Architects copy. Host and update cadence are the team's call.

What publishing looks like — three steps
1
Create the shared repositoryCopy the finished skills/lsc-delivery-architect/ folder and the trigger rule into a repo your competency owns. Include the evaluations — they are how the next maintainer knows a change was safe.
2
Push and confirm the install worksTest it yourself in a fresh project, reload Cursor, and run the validation prompt. Verify the skill routes correctly before you tell anyone it is ready.
3
Share the one-line commandThat is the whole onboarding ask — clone, install, reload, run the validation prompt. No per-person setup session.
Two decisions before you can publish

Who owns it

One person maintains the skill for the competency — typically the delivery lead or a senior architect they nominate. Version history and the evaluation rubric live with that owner.

Where it lives

A shared repository so it can be installed and updated rather than hand-copied. Ownership and location are the only real blockers — the build itself is one session.

Optional grounding indexes
IndexWhat it verifiesIf it is missing
code-review-graphCustom components — callers, dependents, and the tests that cover themFalls back to file search; unverifiable names are marked (proposed)
salesforce-docsStandard LSC objects, fields, and features, with citationsFalls back to the curated catalog reference and flags what it could not confirm

Neither is required. The skill is explicit about what it could not verify, which is the behaviour you want when the alternative is a confident guess.
